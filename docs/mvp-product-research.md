# 商品调研 MVP v0.1

状态：MVP 已实现，等待真实账号小流量验收。范围：美国站、公司内部使用。

## 1. 首版要验证什么

让选品同事输入一个关键词或 ASIN，获得一份能查看数据依据的商品简报，帮助决定“是否值得继续调查”。先验证报告是否有用、数据是否可靠、单次调用成本是否可接受。

完整目标仍是 TikTok Shop + Amazon 多源选品调研。首轮用当前已确认的西柚 Amazon MCP 跑通；TikTok 工具清单和服务器接入方式尚未确认，作为紧接其后的连接器增量。首版不会宣称已经实现跨平台深度调研。多个西柚工具代表多种数据维度，不代表多个独立信源。

“商品调研”是功能名称，不作为新站名。站名、类目、长期信源和评分标准仍由使用者决定。

## 2. 只做一个流程

输入关键词或 ASIN → 查询候选／目标商品 → 补齐指标 → 生成带引用简报 → 保存并回看。

- 市场固定 Amazon US，中文输出，不展示只有一个选项的市场选择器。
- 关键词模式：查询该词近 7 天有竞争流量的商品，按供应商返回顺序取最多 5 个不同 ASIN。页面名称是“关键词相关商品”，不称全站热销榜。没有结果就明确提示，不自动扩大关键词或编造商品。
- ASIN 模式：只研究用户输入的一个 ASIN，不自动扩展竞品。首版限制单个 ASIN；批量输入后续再做。
- 英文商品关键词最直接。中文关键词若需要翻译，先展示建议搜索词让用户编辑，不默默改变研究对象；首轮实现可仅提示输入英文商品关键词。
- 商品均保留 ASIN 与变体口径，不汇总样本总销量，也不据此估计整个市场规模。
- 提交后显示当前阶段，不展示虚构进度百分比或未经实测的完成时间承诺。
- 用户离开页面后后台继续处理；历史列表可重新打开。

## 3. 最少页面

复用现有后台登录、导航和样式，在导航增加“商品调研”。

| 页面 | 内容 |
|---|---|
| `/admin/research` | 关键词／ASIN 输入框、开始调研、历史记录 |
| `/admin/research/:id` | 同一个任务的进度、失败／部分完成说明、报告、证据详情 |

报告只包含四块：

1. **范围**：输入、市场、生成时间、实际数据窗口、来源与缺口。
2. **商品对比**：最多 5 个商品，列出价格、星级／评分数、近 30 天订单指标、近 7 天流量得分和供应商返回的变化指标。
3. **研究结论**：最多 3 条发现，各自关联证据；最多 2 条下一步验证动作。没有证据时明确写“暂不能判断”。
4. **证据清单**：可以展开查看每项指标的来源、统计期、查询时间和保存的数据快照；有实际返回的商品链接时提供原文入口。

每个结论应区分观察与推断。流量得分不写成访客数；供应商订单指标注明其来源和实测／估算／未披露口径；没有成本数据不写利润率，没有评论正文不生成用户痛点结论。商品页链接用于定位商品，不能冒充第三方指标的直接证明。

## 4. 固定数据流程

首版不做自主无限搜索，不生成可视化工作流。

| 步骤 | 关键词模式 | ASIN 模式 |
|---|---|---|
| 确定对象 | `get_keyword_asin_analysis`，US，最多 5 个 ASIN | 本地校验单个 ASIN |
| 关键词背景 | `get_keyword_info`，仅该词 | 跳过 |
| 商品快照 | `get_asin_info`，批量查询 | 查询该 ASIN |
| 近期订单指标 | `get_asin_orders_last_30_days`，批量查询 | 查询该 ASIN |
| 近期流量指标 | `get_asin_traffic`，批量查询 | 查询该 ASIN |
| 写简报 | 代码先整理指标与证据 ID，再由模型生成结构化结论 | 同左 |

关键词工具的定位是“关键词竞争样本”，不等于完整商品搜索或全市场发现。真实接入时先验证返回内容及字段完整性；不可用时停用关键词入口，仍可交付 ASIN 路径，不用模型补商品 ID。

每次 MCP 调用只传该工具当前 schema 声明的字段，不附加后台会话、凭证或无关内部资料。关键词竞争查询固定 `last7days`、按 `traffic desc` 取 5 条；商品信息和流量查询按 `entities` 传 US + ASIN，近 30 天订单查询按 `asins` + `country` 传参。请求摘要会进入回执以便审计，但令牌只存在 worker 的请求头中。

上述工具名、参数形状和数据口径已按西柚公开 MCP／OpenAPI 文档核对，并由本地假服务测试解析；尚未用项目部署账号验证真实返回、延迟和收费。首版不调用类目洞察资源生成工具，也不做自动翻页和长历史回溯。

## 5. 最小技术改动

保持 web → HTTP API → worker／PostgreSQL 的结构。所有模型和 MCP 调用在 worker，打开和刷新页面只读取已保存结果。

- `packages/backend/src/providers/xiyou-mcp.ts`：标准 MCP Streamable HTTP 客户端，执行预算与回执。
- `packages/backend/src/research/xiyou-requests.ts`：五个固定工具的请求 schema。
- `packages/backend/src/research/xiyou-data.ts`：解析并规范化供应商返回值。
- `packages/backend/src/research/run.ts`：固定流程、任务状态、恢复已完成步骤、验证报告引用。
- `packages/backend/src/research/read.ts`：认证后的任务／证据读取。
- `packages/backend/src/jobs/research.ts`：注册一条 `research.run` 队列。
- `packages/contracts/src/research.ts`：请求、状态、报告、证据的数据约定。
- `apps/api/src/routes/admin-research.ts`：复用 `adminHandler`，写操作验证 CSRF。
- `apps/web/app/routes/admin/`：两个页面及证据展开组件。
- `industry/prompts/research-brief.md`：简报结构、引用要求、禁止无依据推断的规则。
- `database/migrations/0039_product_research.sql`：向后兼容地增加调研表和 MCP 预算。

只新增两张业务表：

| 表 | 关键内容 |
|---|---|
| `research_runs` | 输入及类型、US、发起人、提交幂等键、状态、步骤状态 JSON、商品快照 JSON、报告 JSON、流程／提示词版本、错误及起止时间 |
| `research_evidence` | run_id、证据 ID、ASIN／关键词、供应商、工具、脱敏参数摘要、原始返回定位、规范化指标及单位／口径、数据覆盖期、查询时间、来源链接、receipt_id |

原始完整响应保存在现有 receipts 中；证据记录保留足够的规范化快照。保留期必须协调，不能清理回执后让历史报告失去依据。不保存凭证。

不建立长期商品主库、全量商品历史库、独立工作流引擎或多租户系统。完成报告后修改流程，也不覆盖旧报告。

仅需三个接口：

- `POST /api/admin/research-runs`：创建任务；相同提交幂等键返回同一个任务 ID。业务记录与入队同事务。
- `GET /api/admin/research-runs`：分页返回历史列表。
- `GET /api/admin/research-runs/:id`：返回进度、报告和证据。

首版所有后台管理员可查看全部调研，沿用现有权限语义。返回 `no-store`，页面 `noindex`；这些结果不进入 publication、RSS、公开 API、公开 MCP 或站点地图。

## 6. 成本、重试与异常

- 固定流程本身限定关键词任务最多 5 次数据请求、ASIN 任务最多 3 次，并只发起 1 次简报模型请求；任务不会自主扩展工具、翻页或长历史回溯。它们是请求数限制，不是固定金额承诺。
- 新迁移为 `xiyou-mcp` 显式配置全局预算；所有数据请求进入现有回执和预算熔断。
- 同一任务、同一工具及参数的已完成请求复用回执；固定 run_id 和查询上下文，恢复时不改变请求身份。结果未知时沿用现有回执恢复机制，不直接重发；恢复也受任务上限约束。
- 首版不做跨任务时效缓存。用户明确重新调研时创建新任务和新快照，界面提示会重新获取数据并产生调用；查看历史和普通刷新不触发调用。
- 并发和超时遵循供应商实际限制，接入验证后配置。预算耗尽、超时或失败时保存已有证据，返回明确状态。
- 状态为 `queued / running / completed / partial / failed`，步骤状态存在任务 JSON 中。无候选商品是正常空结果；关键数据全无时不生成有判断性的报告。
- 一部分指标失败时生成“部分完成”的简报，缺失显示“暂无数据”，不能当作 0；模型失败时仍保留指标表和证据。
- 模型只返回已提供的证据 ID。后端校验 ID 存在及数字与输入一致；价格和指标表由代码渲染，不让模型重算或补数。来源正文按不可信资料处理，不得改变工具白名单或执行范围。

## 7. 本轮暂缓

全站热门榜、定时监控、关注提醒、长历史图表、综合选品分数、自动利润测算、供应商发现、评论情绪分析、多轮聊天、自动日报、公开分享、PDF／Excel 导出、成员角色体系和可视化编排。

这些能力不影响首版验证“输入 → 有依据的简报 → 回看”。

## 8. TikTok 与多源调研的下一步

1. 核实用户已有 TikTok MCP 的服务器接入方式、授权范围、美国站覆盖、实际工具、字段口径和费用。
2. 优先支持用户提供一个明确的 TikTok 商品链接／ID，增加一个固定取数步骤和独立证据分节。只有视频工具时先做内容观察，不声称具备商品交易数据。
3. 两平台先独立列证据，由用户确认是否同款；不自动汇总指标或给跨平台综合分。
4. 再增加搜索／评论资料连接器，让报告具备真正的多源交叉验证。没有正文来源时，维持缺口说明。

本机或 Codex 中能调用 MCP，不等于部署后的 worker 自动获得授权。服务器可用连接及凭证配置是开发接入检查的第一项；未确认前只使用本地假服务。

## 9. 验收标准

| 场景 | 必须满足 |
|---|---|
| 单 ASIN | 返回该商品及有依据的简报；数字可展开查看来源和统计期 |
| 关键词 | 最多 5 个真实返回的相关 ASIN；展示抽样规则，不冒充全市场榜单 |
| 空结果／错误输入 | 明确提示，不生成商品或填充虚构结论 |
| 部分数据缺失 | 仍可回看已有证据；缺失不当零、不跨窗口混算 |
| 引用检查 | 每个引用 ID 存在；关键数字来自对应证据，实测／估算／未知口径可见 |
| 重复提交／恢复 | 同一个提交键只建一次任务；已完成付费步骤不重跑；恢复仍受预算约束 |
| 历史与权限 | 历史查看不产生调用；未登录不能读取报告或证据；公开出口不泄露内容 |
| 范围诚实 | Amazon 单源报告不称多源调研；无 TikTok 工具时不展示 TikTok 指标 |

实现已用纯本地样本验证 MCP 包装和字段解析。下一步由用户选定一个真实商品做小规模接入验收；开发和自动测试保持外部调用安全阀关闭，按 AGENTS.md 执行类型检查、后端／前端检查及启动后的冒烟检查。

## 10. 开发顺序

1. **接入检查**：服务器 MCP 连接、工具输入输出和费用口径；确认无误后再启用真实调用。
2. **单 ASIN 端到端**：认证、两张表、队列、固定指标、引用简报、历史回看。
3. **关键词入口与异常验收**：候选查询、最多 5 个商品、部分失败、幂等和预算测试。
4. **TikTok 固定步骤**：工具能力确认后按第 8 节增加，复用已有任务与证据结构。

优先看选品同事能否从报告中提出明确的下一步验证动作，再决定扩展监控或评分。
